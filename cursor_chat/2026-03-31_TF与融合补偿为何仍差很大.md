# TF 与融合补偿：为何和手算「差不多」仍要 q_corr / z 标定

## 问题

不关心时间戳；想理解 TF 变化下，为何坐标、姿态与手算差异大到需要补偿。

## 要点

1. **位置**  
   - 同一帧 Keypoints **不同索引**经相同 TF，在 `base_link` 下可差很大（尤其 **z**，末端点 vs 中间点可达米级）。手算「差不多」若与 UI 用的**不是同一点**（如弧长抓取点 vs 某一 kp），会直接表现为「一条链准、一条差」。  
   - `fused_grasp_position_z_offset_m`：**外参/URDF/桥接 z** 的标定叠加，属系统厘米级对齐，不否定 TF 链本身。

2. **姿态**  
   - 「都是大约 90°」在不同**转轴、不同父坐标系**下，四元数可差一个常值旋转；侧抓由切向/法向构造的姿态与桥接 `/object_pose` 的**姿态零位约定**可能不同。  
   - `q_corr`（`q_out = q_corr * q_side`）把融合链的侧抓四元数对齐到与桥接一致的接口语义，不是手算 TF 点积错了。

3. **分工**  
   - **TF**：点/向量在各帧间的几何变换。  
   - **补偿**：在**规划/UI 已采用的约定**上对齐两条感知链，避免同现场不同话题「差一点」导致执行差很多。

## 假设

- 补偿参数含义与 `README.md`、`keypoint_to_arm_tf_node.cpp` 注释一致；未涉及现场真实外参标定值验证。
